## Introduction

We had to launch the service quickly. We divided the pages, developed them simultaneously, and while the requirement for a "responsive design that supports both PC and mobile with a single URL" was clear, we lacked conventions on how to implement it.

Some used CSS media queries, some rendered both mobile and PC versions and hid one, some completely split components into two versions, and some branched logic using JS hooks.

As we entered the maintenance phase, the same "responsive modification" required understanding the structure from scratch each time, as the approach differed per file. Reviews were disrupted by constant switching between files, and with two designs but one codebase, every modification required checking if it broke the other version. Moments of thinking, "Is this right?" became increasingly frequent during development.

## How Our Team Implements Responsive Design

A comprehensive review of the codebase revealed four distinct approaches.

1.  **Inline Media Queries.** The most common choice. Mobile styles are set as default and overridden for desktop. There are commendable aspects — over 98% of files using this method reference central media query tokens, and the mobile-first principle is well-maintained. There was discipline:

```typescript
// SomeButton.css.ts
export const button = style({
  padding: '10px 20px',
  ...tokens.typography['16px'],
  '@media': {
    [tokens.mediaQuery.desktop]: {
      padding: '8px 18px',
      ...tokens.typography['14px'],
    },
  },
});
```

2.  **`display:none` Dual Render.** Both mobile and PC components are rendered side-by-side, and one is hidden with CSS. Both versions always exist in the DOM:

```typescript
// ItemList.tsx
<div className={styles.itemList}>
  <ItemListMobile items={items} />   {/* PC에서 display:none */}
  <ItemListDesktop items={items} />  {/* 모바일에서 display:none */}
</div>
```

```typescript
// ItemList.css.ts — 숨김 규칙
export const mobileWrapper = style({
  display: 'flex', flexDirection: 'column', gap: 16,
  '@media': { [tokens.mediaQuery.desktop]: { display: 'none' } },
});
export const desktopWrapper = style({
  display: 'none',
  '@media': { [tokens.mediaQuery.desktop]: { display: 'block' } },
});
```

My Page-related sections are a hotspot for this pattern (around 40 files using wrappers). From the recent orders section, which mounts the same data as two versions—a carousel (mobile) and a table (PC)—to screens where titles exist in two versions just for a single typography size difference (16px vs 18px):

```typescript
// 프로필 설정 화면의 섹션 제목 — 폰트 크기 하나 때문에 두 벌
<MobileView>
  <Box pt={12} pb={8}>
    <Typography as="p" variant="16px" weight="bold">{section.title}</Typography>
  </Box>
</MobileView>
<DesktopView>
  <Typography as="p" variant="18px" weight="bold">{section.title}</Typography>
</DesktopView>
```

3.  **Complete Component Separation.** For areas with entirely different structures, like headers, files were separated into `DesktopHeader`/`MobileHeader`. Each file is a single layout without `@media`, so it can be read considering only one device:

```typescript
// DesktopHeader.tsx — @media 없는 단일 레이아웃
export function DesktopHeader({ leftSlot, centerSlot, rightSlot }: DesktopHeaderProps) {
  return (
    <header role="banner">
      <nav className={styles.container} aria-label="Desktop header navigation">
        <div className={styles.logoSlot}>{leftSlot ?? <Logo height={24} />}</div>
        <div className={styles.centerSlot}>{centerSlot}</div>
        <div className={styles.actionsSlot}>{rightSlot}</div>
      </nav>
    </header>
  );
}
// MobileHeader.tsx는 햄버거 버튼 + 검색 아이콘 구조로 완전히 다른 파일
```

However, the branching point for choosing between the two ultimately fell back to B (dual render) — while file separation was clean, there was no standard for "what to use as the branching point":

```typescript
// 분기점 — 두 벌을 모두 렌더하고 CSS로 토글 (C와 B의 조합)
<MobileView><MobileHeader /></MobileView>
<DesktopView><DesktopHeader /></DesktopView>
```

There are also cases where complete separation was done, but the branching point choice differed. All 8 sections of the membership page consist of Desktop/Mobile function pairs, but the selection is made by JS, not CSS:

```typescript
// 멤버십 등급 배너 — 약 160줄 (Desktop 함수 + Mobile 함수)
function TierBannerDesktop() {
  const { data } = useSuspenseQuery(membershipQueries.summary());
  // …등급 계산, 진행률, 실적 모달 핸들러…
  return <Box className={styles.desktopBanner}>{/* 가로 배너 + 우측 카드 */}</Box>;
}
function TierBannerMobile() {
  const { data } = useSuspenseQuery(membershipQueries.summary());
  // …완전히 같은 로직이 한 번 더…
  return <VStack px={16}>{/* 세로 스택 + 말풍선 카드 */}</VStack>;
}
export function TierBanner() {
  const platform = usePlatform(); // SSR 초기값 'PC' 고정 + matchMedia 판정
  return platform === 'PC' ? <TierBannerDesktop /> : <TierBannerMobile />;
}
```

The two functions have identical data hooks and calculation logic, differing only in JSX (approx. 30 lines of duplication). While separated, shared logic was not extracted, leading to duplication, and since the branching is done by JS, the SSR cost remains the same.

4.  **JS Hook Prop Branching.** Within a single component, values, text, and spacing are all branched using ternary operators:

```typescript
// OrderInfoRow.tsx
const isMobile = useIsMobile();
const isDesktop = useIsDesktop();
return (
  <div>
    {isDesktop && <span className={styles.divider}>|</span>}
    <span>{isMobile && 'No. '}{orderNo}</span>
    ...
    <Space size={isMobile ? 16 : 24} />
    <Space size={isMobile ? 32 : 56} />
  </div>
);
```

All four methods "work." The problem is that they coexist within a single codebase, and even mix within a single screen.

The four patterns not only vary by file but also mix within a single page — My Page is a hotspot for B, while Membership uses C for separation and D for selection. Real-world examples are included in each pattern description.

## Actual Inconveniences Experienced During Development

The situations above are statistics; below are the daily experiences.

### 1. CSS Complexity — One File Responsible for Two Layouts

The real problem isn't just value differences like font size. It's **when a single file is simultaneously responsible for two UIs with fundamentally different layout structures**. The review detail popup style file is **over 500 lines long with 26 `@media` blocks** — it's a vertical stack on mobile and a two-column layout on PC, so almost every selector has an inverted branch:

```typescript
// ReviewPopup.css.ts (500여 줄 중) — 세로 스택 ↔ 좌우 2단 전환
export const container = style({
  display: 'flex',
  flexDirection: 'column',   // 모바일: 세로 스택
  height: '100%',
  '@media': {
    [tokens.mediaQuery.desktop]: {
      flexDirection: 'row',  // PC: 좌우 배치로 전환
      height: '640px',
      gap: '32px',
    },
  },
});
export const contentPane = style({
  width: '100%',             // 모바일: 전체 폭
  paddingTop: '24px',
  '@media': {
    [tokens.mediaQuery.desktop]: {
      width: '50%',          // PC: 절반 폭
      padding: 0,
    },
  },
});
```

The common overlay goes a step further, with a single file responsible for **two distinct components: a mobile bottom sheet and a PC central modal**:

```typescript
// OverlayLayer.css.ts — 바텀시트 ↔ 모달 전환
const dimmed = style({
  position: 'fixed',
  inset: 0,
  display: 'flex',
  justifyContent: 'center',
  alignItems: 'end',          // 모바일: 하단 정렬 (바텀시트)
  '@media': {
    [tokens.mediaQuery.desktop]: {
      alignItems: 'center',   // PC: 중앙 정렬 (모달)
    },
  },
});
const panel = style({
  width: '100%',
  borderRadius: '16px 16px 0 0',      // 모바일: 위쪽만 둥글게
  transform: 'translate(0, 100%)',    // 모바일: 하단 오프스크린에서 올라옴
  '@media': {
    [tokens.mediaQuery.desktop]: {
      borderRadius: 0,                // PC: 모서리 없음
      width: '480px',
    },
  },
});
```

The CTA button on the payment page is a fixed bar at the bottom of the screen on mobile, and inline within the content on PC — `position: fixed ↔ static` is inverted within a single style block. On top of this, `14px→16px` type typography pairs are repeated across dozens of files. These files are not actually "one responsive file," but rather **two different UIs compressed into a single file**.

### 2. Constant Switching Between `tsx` and `css.ts` During Review and Modification

To understand a single layout change during code review, one must read the `.tsx` file, then go to the `.css.ts` file to find the class, and then return to check the conditions. What's worse is **when a single component uses both CSS branching and JS branching simultaneously** — product details change `flex-order` with `@media` in `.css.ts` while branching margins with `isMobile ? 16 : 0` in `.tsx`. Understanding one layout requires navigating **two files and two mechanisms**.

### 3. Designs Come in Two Versions, But the Code is One

-   Both design mockups and feature requests come in **two versions: mobile/desktop**. However, the code is merged into a single file.
-   QA and testing also always involve two versions — if one side is fixed, it's necessary to check every time if the other side is broken.
-   This is critical when working with AI: "Apply mobile design" and "Apply PC design" **modify the same file, making parallel work impossible**. If the files were separated, two agents (or two people) could work simultaneously.

## Why Does Development Feel So Inconvenient and Difficult?

I wanted to confirm whether the inconvenience was merely a matter of familiarity or a structural problem explainable by principles. Toss [frontend-fundamentals](https://frontend-fundamentals.com/) defines good code by four criteria: **Readability, Predictability, Cohesion, and Coupling**. I took examples directly from four representative documents and applied our responsive code to the same format.

### 1. Separate Code That Doesn't Run Together — Readability

The [original text](https://frontend-fundamentals.com/code-quality/code/examples/submit-button.html) uses a button that behaves differently based on permissions as an example:

```typescript
// 토스 원문 — Before
function SubmitButton() {
  const isViewer = useRole() === "viewer";
  useEffect(() => {
    if (isViewer) return;
    showButtonAnimation();
  }, [isViewer]);
  return isViewer ? (
    <TextButton disabled>Submit</TextButton>
  ) : (
    <Button type="submit">Submit</Button>
  );
}
```

> Code that doesn't execute simultaneously appears interleaved, making it harder to understand.

Now, if we replace `isViewer` with `isMobile`, we can see that pattern D from Chapter 1 is exactly the same as the "Before" example in the original text. Looking directly at our code:

```typescript
// 우리 코드 — Before: 모바일에서 절대 실행되지 않는 PC 코드가 같은 JSX에 교차
function OrderInfoRow({ orderNo }: Props) {
  const isMobile = useIsMobile();
  const isDesktop = useIsDesktop();
  return (
    <div>
      {isDesktop && <span className={styles.divider}>|</span>}
      <span>{isMobile && 'No. '}{orderNo}</span>
      <Space size={isMobile ? 16 : 24} />
      <Space size={isMobile ? 32 : 56} />
    </div>
  );
}
```

There are approximately 370 such interweavings in the codebase.

The improvement in the original text is to completely separate components by permission:

```typescript
// 토스 원문 — After
function SubmitButton() {
  const isViewer = useRole() === "viewer";
  return isViewer ? <ViewerSubmitButton /> : <AdminSubmitButton />;
}
function ViewerSubmitButton() {
  return <TextButton disabled>Submit</TextButton>;
}
function AdminSubmitButton() {
  useEffect(() => {
    showButtonAnimation();
  }, []);
  return <Button type="submit">Submit</Button>;
}
```

Improving our code in the same way results in each version becoming straight-line code without branching:

```typescript
// 우리 코드 — After: 분기는 한 곳, 각 벌은 조건 0개
function OrderInfoRow(props: Props) {
  const isMobile = useIsMobile();
  return isMobile ? <OrderInfoRowMobile {...props} /> : <OrderInfoRowDesktop {...props} />;
}
function OrderInfoRowMobile({ orderNo }: Props) {
  return (
    <div>
      <span>{'No. '}{orderNo}</span>
      <Space size={16} />
    </div>
  );
}
function OrderInfoRowDesktop({ orderNo }: Props) {
  return (
    <div>
      <span className={styles.divider}>|</span>
      <span>{orderNo}</span>
      <Space size={24} />
    </div>
  );
}
```

### 2. Reduce Context Switching — Readability

The [original text](https://frontend-fundamentals.com/code-quality/code/examples/user-policy.html) shows code where understanding why a button is disabled requires three jumps:

```typescript
// 토스 원문 — Before: "Invite 버튼이 왜 비활성화지?" 하나에 세 번 점프
<Button disabled={!policy.canInvite}>Invite</Button>      // ① policy.canInvite는 어디서?

const policy = getPolicyByRole(user.role);                 // ② getPolicyByRole은 뭐를 하지?

function getPolicyByRole(role) {
  return { canInvite: POLICY_SET[role].includes("invite") }; // ③ POLICY_SET까지 와서야 답
}
const POLICY_SET = { admin: ["invite", "view"], viewer: ["view"] };
```

> Three jumps just to answer "Why is the Invite button disabled?"

Looking at a real-world example from our code, it's even more dramatic. The path to understanding **when a single share button is visible** in the event header component:

```typescript
// EventHeader.tsx — ① JS가 isMobile로 플로팅 버튼의 '상태'를 계산
const getFloatingPosition = (isMobile, isAtTop, isScrollingDown) => {
  if (!isMobile) return 'hidden';        // ② JS 분기: PC면 숨김…이긴 한데
  if (!isAtTop && isScrollingDown) return 'bottom';
  if (isAtTop && !isScrollingDown) return 'stackOne';
  return 'stackTwo';
};
// …
<div className={styles.staticShareArea}>{shareButton}</div>              {/* ③ 클래스 확인 */}
<div className={styles.floatingShareArea({ position })}>{shareButton}</div>
```

```typescript
// EventHeader.css.ts — ④ 같은 버튼들의 가시성이 @media로 '또' 제어된다
export const staticShareArea = style({
  display: 'none',                       // 모바일: 정적 버튼 숨김
  '@media': { [tokens.mediaQuery.desktop]: { display: 'flex' } },
});
export const floatingShareArea = recipe({
  base: {
    position: 'fixed',
    '@media': { [tokens.mediaQuery.desktop]: { display: 'none' } },  // PC: 플로팅 통째로 숨김
  },
  variants: { position: { bottom: { bottom: 32 }, stackOne: { bottom: 64 }, stackTwo: { bottom: 112 }, hidden: { opacity: 0 } } },
});
```

The visibility of the same share button is **dually controlled by two mechanisms: JS (`isMobile` → position calculation) and CSS (`@media display:none`)**. Answering "Why isn't this button visible on PC?" requires navigating multiple code sections, despite being a simple question.

### 3. Allow Duplicate Code — Coupling

The [original text](https://frontend-fundamentals.com/code-quality/code/examples/use-bottom-sheet.html) shows a commonized hook that is repeated across multiple pages, issuing a warning:

```typescript
// 토스 원문 — 공통화된 점검 바텀시트 훅
export const useOpenMaintenanceBottomSheet = () => {
  const maintenanceBottomSheet = useMaintenanceBottomSheet();
  const logger = useLogger();
  return async (maintainingInfo: TelecomMaintenanceInfo) => {
    logger.log("점검 바텀시트 열림");
    const result = await maintenanceBottomSheet.open(maintainingInfo);
    if (result) {
      logger.log("점검 바텀시트 알림받기 클릭");
    }
    closeView();
  };
};
```

> If there's a possibility for behavior to differ per page, allowing duplicate code without commonization is a better choice.

We violated this principle in the opposite direction. We commonized two layouts into one file, reasoning that "PC and mobile are the same screen," but actual requests come in separately.

```typescript
// 우리 코드 — Before: OrderSkeleton.tsx, isMobile 삼항이 37번
export const OrderSkeleton = () => {
  const isMobile = useIsMobile();
  return (
    <>
      <Skeleton width="100%" height={isMobile ? 46 : 62} borderRadius={isMobile ? 0 : 4} />
      <Space size={isMobile ? 0 : 40} />
      <Skeleton width={isMobile ? 144 : 130} height={isMobile ? 32 : 24} />
      {!isMobile && <div className={styles.line} />}
      {isMobile ? <div className={styles.divider} /> : <Space size={48} />}
      <Skeleton width={160} height={isMobile ? 18 : 22} />
      <Space size={isMobile ? 2 : 4} />
      {/* …이런 삼항이 파일 전체에 37번 */}
    </>
  );
};
```

This is the result of trying to put two completely different skeleton layouts into one function "without duplication." If duplication is allowed, each file becomes straight-line code without conditions:

```typescript
// 우리 코드 — After: 레이아웃 중복을 허용하고 두 벌로
export const OrderSkeleton = () => (
  <>
    <MobileView><OrderSkeletonMobile /></MobileView>
    <DesktopView><OrderSkeletonDesktop /></DesktopView>
  </>
);
function OrderSkeletonMobile() {
  return (
    <>
      <Skeleton width="100%" height={46} borderRadius={0} />
      <Skeleton width={144} height={32} />
      <div className={styles.divider} />
      {/* 조건 분기 0개 — 위에서 아래로 그냥 읽힌다 */}
    </>
  );
}
// OrderSkeletonDesktop도 동일 — 37개의 삼항이 사라지고 단순한 목록 둘이 남는다
```

The 500-line, 26-`@media` file from Chapter 2 tells the same story. It's a structure where modifying the mobile design can break the PC version, a state where, as the original text states, "every time common code is modified, dependent code must be individually tested."

### 4. Expose Hidden Logic — Predictability

The [original text](https://frontend-fundamentals.com/code-quality/code/examples/hidden-logic.html) uses logging secretly embedded within a balance inquiry function as an example:

```typescript
// 토스 원문 — Before
async function fetchBalance(): Promise<number> {
  const balance = await http.get<number>("...");
  logging.log("balance_fetched");   // 이름·반환 타입으로 예측할 수 없는 숨은 동작
  return balance;
}
```

> Only logic that can be predicted by the function's name, parameters, and return type should remain in the implementation.

In our code, this "smell" manifests as **hidden device logic within components**. It's not apparent from the name and signature alone, but it hides or disappears internally:

```typescript
// 우리 코드 — Before ①: 이름만 보면 항상 렌더될 것 같은 섹션
export const RecentOrdersSection = () => {
  const isMobile = useIsMobile();
  const { data, isLoading } = useQuery(ordersQuery);
  const orders = data?.orders ?? [];
  // 모바일 + 주문 없음 → 섹션이 통째로 사라진다. 호출부는 알 길이 없다
  if (isLoading || (isMobile && !orders.length)) return null;
  return <section>…</section>;
};
```

```typescript
// 우리 코드 — Before ②: JSX에는 항상 있는데, 모바일에서는 CSS가 몰래 숨긴다
// SectionTitle.css.ts
export const title = style({
  display: 'none', // 기본(모바일): 숨김 — tsx만 읽는 사람은 알 수 없다
  '@media': { [tokens.mediaQuery.desktop]: { display: 'block' } },
});
```

The `tsx` file cannot answer the question, "Why isn't this title visible on mobile?" — the hidden logic is in the CSS. The improvement is the same as in the original text: expose the hiding mechanism not within the implementation, but **in the name and call site**:

```typescript
// 우리 코드 — After: 조건은 호출부로, 디바이스 전용임은 래퍼/이름으로
{(!isMobile || orders.length > 0) && <RecentOrdersSection orders={orders} />}

<DesktopView>
  <SectionTitle>Order Details</SectionTitle>  {/* CSS의 몰래 display:none 대신 */}
</DesktopView>
```

### Summary — The Same Signal Across All Four Criteria

| Criteria        | Principle                               | Our Symptoms                                                              |
| --------------- | --------------------------------------- | ------------------------------------------------------------------------- |
| Readability     | Separate code that doesn't run together | `isMobile ? A : B` interweavings in ~370 places — code for two devices mixed in one function |
| Readability     | Reduce context switching                | `tsx` ↔ `css.ts` ↔ tokens, round trips across file boundaries are the default reading path |
| Coupling        | Allow duplicate code                    | Layouts with two distinct designs combined into one file → ~500 lines / 26 `@media` blocks |
| Predictability  | Expose hidden logic                     | Component hides itself internally based on device conditions              |

## How Do Other Popular E-commerce Sites Do It?

Since I had never developed two versions of a web application (PC/mobile) rather than just a simple responsive one, I wondered what the standard approach would be. So, I asked fable to research popular e-commerce sites.

### 1. Product List Measurements

| Site          | Stack                       | Implementation                            | Decisive Evidence                                                                   |
| ------------- | --------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------- |
| 29CM          | React + Tailwind            | 🟢 **Media Query Responsive (Single Class)** ⭐ | `grid grid-cols-3 desktop:grid-cols-5` — Same DOM, same class switches between 3 columns ↔ 5 columns |
| Ohouse Home   | React SSR + Emotion         | 🟢 CSS Media Queries + Local Dual Render  | 171 media rules (768·1024·1256px + hover:hover 30 times). Only `stats-mobile`/`stats-pc` pairs are toggled. |
| Ohouse Store  | Next.js + Emotion           | 🟠 **JS (`matchMedia`) Branching**        | Ranking grid: no rule exists for 375px iframe, **0 `@media` rules but responds to viewport** = renders a different tree |
| Kurly         | Next.js + Emotion (effectively CSR) | 🔴 **User Agent Adaptive — PC Fixed Width** | Both 375/1280 iframes have 3 columns, 249px cards identical. Main 1050px fixed. The reality of "single URL" is user agent branching. |
| Musinsa       | Next.js + styled-components | 🔴 **User Agent Adaptive (Fluid)**        | Fluid expansion of a single mobile layout (min 744/max 1440). Consistent with PC web termination in 2024. |

### 2. Home Screen Measurements — Screens with Significantly Divergent Structures

| Site          | Branching Mechanism               | Page Layout                                   | Header·GNB                                                | Bottom Tab Bar / Partial UI                                | SSR Status                 |
| ------------- | --------------------------------- | --------------------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------- | -------------------------- |
| 29CM          | 🟢 Viewport + CSS Toggle          | Magazine-style 3 columns (PC) ↔ Single hero (MO) | Both PC GNB and mobile tab bar exist in DOM — `hidden`/`desktop:flex` symmetrical toggle | Bottom tab bar is hidden with `desktop:hidden`, app webview is further hidden with `webview:hidden` | Both versions server-rendered |
| Ohouse Home   | 🟢 CSS Media Queries (Single DOM) | Single DOM rearrangement — 38 main sections are identical | Same header tree rearranged across two widths             | Horizontal scroll sections mobile 4 vs PC 1 — carouselization also via CSS | SSR 322KB, device markers 0 |

| Musinsa       | 🔴 User Agent Adaptive (Fluid)    | DOM effectively identical (2,876 vs 2,880 nodes), only width is fluid (744~1440) | GNB identical — tracking metadata starts with `pc_gnb`    | 5 horizontal scroll carousels identical                    | Device markers exist in SSR |

### Research Findings

To summarize the research findings in one sentence: **Everyone is doing it differently.** From pure media query responsive design (Coupang, 29CM) to JS branching (Ohouse Store), user agent adaptive (Kurly, Musinsa), and domain separation (Olive Young Korea), all are actively in use.

The reason everyone has made different choices is likely due to the respective trade-offs, as shown below.

| Method                            | Pros                                                              | Cons                                                                      | Adoption Examples                                 |
| --------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------- |
| **① CSS Media Queries** (Single DOM) | SSR-safe (server doesn't need to know the device) · zero-runtime · immediate response to resize | Expressive limitations if DOM structure differs significantly · complexity explodes if branching accumulates per selector | Coupang · 29CM · Ohouse Home · Our product list   |
| **② `display:none` Dual Render**  | Branches UIs with different structures using only CSS · simple implementation | Dual DOM/bundle transfer · SEO duplicate content · significant waste if more than one screen's worth (accessibility is safe with `display:none` — 5-4) | 29CM GNB · Ohouse local fragments · Our header/order list |
| **③ JS Branching** (`matchMedia` hook) | Renders only one DOM version · clearly expressed with logic       | SSR initial value issue → hydration mismatch or 2-pass render (slow) · flickering/CLS before detection | Ohouse Store · Our `useIsMobile` 374 times        |
| **④ Server User Agent Detection** | Accurate from first render · opposite code not sent (bundle -38.7% measured case) · safe hydration | No viewport resize response · risk of tablet/new user agent detection issues | Market Kurly · Musinsa                            |
| **⑤ Component/Route Separation**  | File = design 1:1 · parallel work possible · each file is a single layout without `@media` | Branching point design needed (must combine with ④ for full SSR) · risk of dual modification for common logic/copy | Our `DesktopHeader`/`MobileHeader` · Velog route separation measured |

## Essential Considerations for Responsive Implementation

To approach how to develop, I felt it was necessary to first understand the problems that would inevitably arise regardless of the chosen method. So, I investigated at least these points first.

### 1. Bundle Size

Media query and dual-render methods mean mobile users download all PC code (and vice-versa).

Here's an important distinction. Server user agent "detection" alone does not reduce the bundle size. Our app already uses user agents (for app webview detection, bot detection to choose SSR streaming strategy), but none of this is linked to the bundle. Bundle composition is determined by the static import graph at build time, so even if the server knows the device, if "which JS to send" isn't branched, it remains the same. Bundle size reduction requires a combination of detection + serving separation (route separation or dynamic import).

### 2. SEO

-   Google uses mobile-first indexing — the mobile DOM must be the complete version of the content.
-   `display:none` dual render creates duplicate content. While crawlers read hidden content, if the management of the two versions diverges, it becomes ambiguous which one is canonical.
-   User agent detection provides different HTML to Googlebot user agents (mobile/desktop versions), so caching management is needed to avoid being mistaken for cloaking.

### 3. Hydration Mismatch

This is inevitably encountered when using JS branching (③) in SSR. Since the server doesn't know the device, it fixes an initial value (we use `desktop`), and if this differs from the client's determination, React throws a mismatch. A 2-pass render (`isHydrated` gate) that safely bypasses this, however, incurs **flickering and CLS** instead. Our footer is paying precisely this cost:

```typescript
// 푸터 앱 다운로드 섹션 — hydration 후에야 등장 → 늦은 팝인, CLS
{isHydrated && platform !== 'APP' && (
  <>
    <div className={styles.appBannerDesktop}>…QR코드…</div>
    <div className={styles.appBannerMobile}>…스토어 배지…</div>
  </>
)}
```
