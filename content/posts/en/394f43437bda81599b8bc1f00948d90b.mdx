## Introduction

We had to launch the service quickly. We divided the pages, developed them simultaneously, and while the requirement for a "responsive design that supports both PC and mobile with a single URL" was clear, we lacked conventions on how to implement it.

Some used CSS media queries, some rendered both mobile and PC versions and hid one, some completely split components into two versions, and some branched logic using JS hooks.

Once we entered the maintenance phase, the same "responsive modification" required understanding the structure from scratch every time, as the approach differed per file. Reviews were disrupted by constantly switching between files, and with two designs but one codebase, we had to repeatedly check if a single modification broke the other version. Moments of "Is this right?" became increasingly frequent during development.

## How Our Team Implements Responsive Design

A comprehensive review of the codebase revealed four distinct approaches.

1.  **Inline Media Queries.** The most common choice. Mobile styles are set as default and overridden for desktop. There are commendable aspects — over 98% of files using this method reference central media query tokens, and the mobile-first principle is well-maintained. There was discipline:

```typescript
// SomeButton.css.ts
export const button = style({
  padding: '10px 20px',
  ...tokens.typography['16px'],
  '@media': {
    [tokens.mediaQuery.desktop]: {
      padding: '8px 18px',
      ...tokens.typography['14px'],
    },
  },
});
```

2.  **`display:none` Dual Render.** Both mobile and PC components are rendered side-by-side, and one is hidden with CSS. Both versions always exist in the DOM:

```typescript
// ItemList.tsx
<div className={styles.itemList}>
  <ItemListMobile items={items} />   {/* display:none on PC */}
  <ItemListDesktop items={items} />  {/* display:none on mobile */}
</div>
```

```typescript
// ItemList.css.ts — Hiding Rules
export const mobileWrapper = style({
  display: 'flex', flexDirection: 'column', gap: 16,
  '@media': { [tokens.mediaQuery.desktop]: { display: 'none' } },
});
export const desktopWrapper = style({
  display: 'none',
  '@media': { [tokens.mediaQuery.desktop]: { display: 'block' } },
});
```

My Page sections are a dense area for this pattern (around 40 files using wrappers). From the recent orders section, which mounts the same data as two versions—a carousel (mobile) and a table (PC)—to screens where even a single typography size difference (16px vs 18px) results in two versions of a title:

```typescript
// Section title on profile settings screen — two versions due to a single font size
<MobileView>
  <Box pt={12} pb={8}>
    <Typography as="p" variant="16px" weight="bold">{section.title}</Typography>
  </Box>
</MobileView>
<DesktopView>
  <Typography as="p" variant="18px" weight="bold">{section.title}</Typography>
</DesktopView>
```

3.  **Complete Component Separation.** For areas with entirely different structures, like headers, files were separated into `DesktopHeader`/`MobileHeader`. Each file is a single layout without `@media`, so it can be read by considering only one device:

```typescript
// DesktopHeader.tsx — Single layout without @media
export function DesktopHeader({ leftSlot, centerSlot, rightSlot }: DesktopHeaderProps) {
  return (
    <header role="banner">
      <nav className={styles.container} aria-label="Desktop header navigation">
        <div className={styles.logoSlot}>{leftSlot ?? <Logo height={24} />}</div>
        <div className={styles.centerSlot}>{centerSlot}</div>
        <div className={styles.actionsSlot}>{rightSlot}</div>
      </nav>
    </header>
  );
}
// MobileHeader.tsx is a completely different file with a hamburger button + search icon structure
```

However, the branching point for choosing between the two ultimately used approach B (dual render) — file separation was clean, but there was no standard for "what should be the branching point":

```typescript
// Branching point — renders both versions and toggles with CSS (combination of C and B)
<MobileView><MobileHeader /></MobileView>
<DesktopView><DesktopHeader /></DesktopView>
```

There are also cases where complete separation is used, but the branching point selection differs. All 8 sections of the membership page consist of Desktop/Mobile function pairs, but the selection is made by JS, not CSS:

```typescript
// Membership tier banner — approx. 160 lines (Desktop function + Mobile function)
function TierBannerDesktop() {
  const { data } = useSuspenseQuery(membershipQueries.summary());
  // …tier calculation, progress, performance modal handler…
  return <Box className={styles.desktopBanner}>{/* Horizontal banner + right card */}</Box>;
}
function TierBannerMobile() {
  const { data } = useSuspenseQuery(membershipQueries.summary());
  // …exactly the same logic again…
  return <VStack px={16}>{/* Vertical stack + speech bubble card */}</VStack>;
}
export function TierBanner() {
  const platform = usePlatform(); // SSR initial value fixed to 'PC' + matchMedia determination
  return platform === 'PC' ? <TierBannerDesktop /> : <TierBannerMobile />;
}
```

The two functions have identical data hooks and calculation logic, differing only in JSX (approx. 30 lines of duplication). While separated, shared logic was not extracted, leading to duplication, and since the branching is in JS, the SSR cost remains the same.

4.  **JS Hook Prop Branching.** Within a single component, values, text, and spacing are all branched using ternary operators:

```typescript
// OrderInfoRow.tsx
const isMobile = useIsMobile();
const isDesktop = useIsDesktop();
return (
  <div>
    {isDesktop && <span className={styles.divider}>|</span>}
    <span>{isMobile && 'No. '}{orderNo}</span>
    ...
    <Space size={isMobile ? 16 : 24} />
    <Space size={isMobile ? 32 : 56} />
  </div>
);
```

All four methods "work." The problem is that they coexist within a single codebase and are even mixed within a single screen.

The four patterns not only vary by file but also mix within a single page — My Page is a dense area for B, while Membership uses C for separation and D for selection. Real-world examples are included with each pattern description.

## Actual Inconveniences Experienced During Development

The above describes the current situation, and below are the inconveniences I've felt.

### 1. CSS Complexity — One File Responsible for Two Layouts

The real problem isn't value differences like font size. It's **when a single file is simultaneously responsible for two UIs with fundamentally different layout structures.** The review detail popup style file is **over 500 lines with 26 `@media` blocks** — it's a vertical stack on mobile and a two-column layout on PC, so almost every selector has an inverted branch:

```typescript
// ReviewPopup.css.ts (out of ~500 lines) — Vertical stack ↔ Two-column layout switch
export const container = style({
  display: 'flex',
  flexDirection: 'column',   // Mobile: Vertical stack
  height: '100%',
  '@media': {
    [tokens.mediaQuery.desktop]: {
      flexDirection: 'row',  // PC: Switches to horizontal layout
      height: '640px',
      gap: '32px',
    },
  },
});
export const contentPane = style({
  width: '100%',             // Mobile: Full width
  paddingTop: '24px',
  '@media': {
    [tokens.mediaQuery.desktop]: {
      width: '50%',          // PC: Half width
      padding: 0,
    },
  },
});
```

The common overlay takes it a step further, with a single file responsible for **two distinct components: a mobile bottom sheet and a PC central modal**:

```typescript
// OverlayLayer.css.ts — Bottom sheet ↔ Modal switch
const dimmed = style({
  position: 'fixed',
  inset: 0,
  display: 'flex',
  justifyContent: 'center',
  alignItems: 'end',          // Mobile: Aligned to bottom (bottom sheet)
  '@media': {
    [tokens.mediaQuery.desktop]: {
      alignItems: 'center',   // PC: Centered (modal)
    },
  },
});
const panel = style({
  width: '100%',
  borderRadius: '16px 16px 0 0',      // Mobile: Rounded only at the top
  transform: 'translate(0, 100%)',    // Mobile: Slides up from off-screen bottom
  '@media': {
    [tokens.mediaQuery.desktop]: {
      borderRadius: 0,                // PC: No rounded corners
      width: '480px',
    },
  },
});
```

The CTA button on the payment page is a fixed bottom bar on mobile and inline within the content on PC — `position: fixed ↔ static` is inverted within a single style block. On top of this, `14px→16px` type typography pairs are repeated across dozens of files. These files are not truly "one responsive file" but rather **two different UIs compressed into a single file.**

### 2. Constant Switching Between `tsx` ↔ `css.ts` During Review and Modification

To understand a single layout change during code review, one must read the `.tsx` file, then go to the `.css.ts` file to find the class, and then return to check the conditions. What's worse is **when a single component uses both CSS branching and JS branching simultaneously** — product details change `flex-order` with `@media` in `.css.ts` while branching margins with `isMobile ? 16 : 0` in `.tsx`. Understanding a single layout requires navigating between **two files and two mechanisms.**

### 3. Designs Come in Two Versions, But Code is in One

-   Both design mockups and product requests come in **two versions: mobile/desktop**. However, the code is merged into a single file.
-   QA and testing also always involve two versions — if one side is fixed, we must constantly check if the other side is broken.
-   This is critical when working with AI: "Apply mobile design" and "Apply PC design" **modify the same file, making parallel work impossible.** If the files were separated, two agents (or two people) could work simultaneously.

## Why Does Development Feel So Inconvenient and Difficult?

I wanted to determine if the inconvenience was merely a matter of familiarity or a structural problem explainable by principles.

Toss's [frontend-fundamentals](https://frontend-fundamentals.com/) defines good code by four criteria: **Readability, Predictability, Cohesion, and Coupling.** I've taken examples directly from four representative documents and applied our responsive code to the same format.

### 1. Separating Code That Doesn't Execute Together — Readability

The [original text](https://frontend-fundamentals.com/code-quality/code/examples/submit-button.html) gives an example of a button that behaves differently based on permissions:

```typescript
// Toss Original — Before
function SubmitButton() {
  const isViewer = useRole() === "viewer";
  useEffect(() => {
    if (isViewer) return;
    showButtonAnimation();
  }, [isViewer]);
  return isViewer ? (
    <TextButton disabled>Submit</TextButton>
  ) : (
    <Button type="submit">Submit</Button>
  );
}
```

> Code that doesn't execute simultaneously appears interleaved, creating a burden when trying to understand the code.

Now, if we replace `isViewer` with `isMobile`, we can see that pattern D from Chapter 1 is exactly the same as the "Before" example in the original text. Looking directly at our code:

```typescript
// Our Code — Before: PC code that never executes on mobile is interleaved in the same JSX
function OrderInfoRow({ orderNo }: Props) {
  const isMobile = useIsMobile();
  const isDesktop = useIsDesktop();
  return (
    <div>
      {isDesktop && <span className={styles.divider}>|</span>}
      <span>{isMobile && 'No. '}{orderNo}</span>
      <Space size={isMobile ? 16 : 24} />
      <Space size={isMobile ? 32 : 56} />
    </div>
  );
}
```

There are over 370 such interweavings in the codebase.

The improvement in the original text is to completely separate components by permission:

```typescript
// Toss Original — After
function SubmitButton() {
  const isViewer = useRole() === "viewer";
  return isViewer ? <ViewerSubmitButton /> : <AdminSubmitButton />;
}
function ViewerSubmitButton() {
  return <TextButton disabled>Submit</TextButton>;
}
function AdminSubmitButton() {
  useEffect(() => {
    showButtonAnimation();
  }, []);
  return <Button type="submit">Submit</Button>;
}
```

Improving our code in the same way results in each version becoming straight-line code without branching:

```typescript
// Our Code — After: One branching point, zero conditions per version
function OrderInfoRow(props: Props) {
  const isMobile = useIsMobile();
  return isMobile ? <OrderInfoRowMobile {...props} /> : <OrderInfoRowDesktop {...props} />;
}
function OrderInfoRowMobile({ orderNo }: Props) {
  return (
    <div>
      <span>{'No. '}{orderNo}</span>
      <Space size={16} />
    </div>
  );
}
function OrderInfoRowDesktop({ orderNo }: Props) {
  return (
    <div>
      <span className={styles.divider}>|</span>
      <span>{orderNo}</span>
      <Space size={24} />
    </div>
  );
}
```

### 2. Reducing Context Switching — Readability

The [original text](https://frontend-fundamentals.com/code-quality/code/examples/user-policy.html) shows code where understanding why a button is disabled requires three jumps:

```typescript
// Toss Original — Before: Three jumps to understand "Why is the Invite button disabled?"
<Button disabled={!policy.canInvite}>Invite</Button>      // ① Where does policy.canInvite come from?

const policy = getPolicyByRole(user.role);                 // ② What does getPolicyByRole do?

function getPolicyByRole(role) {
  return { canInvite: POLICY_SET[role].includes("invite") }; // ③ Only at POLICY_SET do we get the answer
}
const POLICY_SET = { admin: ["invite", "view"], viewer: ["view"] };
```

Looking at a real-world example from our code, it's even more dramatic. The path to understanding **when a single share button appears** in the event header component:

```typescript
// EventHeader.tsx — ① JS calculates the 'state' of the floating button with isMobile
const getFloatingPosition = (isMobile, isAtTop, isScrollingDown) => {
  if (!isMobile) return 'hidden';        // ② JS branch: Hidden on PC... but then
  if (!isAtTop && isScrollingDown) return 'bottom';
  if (isAtTop && !isScrollingDown) return 'stackOne';
  return 'stackTwo';
};
// …
<div className={styles.staticShareArea}>{shareButton}</div>              {/* ③ Check class */}
<div className={styles.floatingShareArea({ position })}>{shareButton}</div>
```

```typescript
// EventHeader.css.ts — ④ Visibility of the same buttons is 'again' controlled by @media
export const staticShareArea = style({
  display: 'none',                       // Mobile: Static button hidden
  '@media': { [tokens.mediaQuery.desktop]: { display: 'flex' } },
});
export const floatingShareArea = recipe({
  base: {
    position: 'fixed',
    '@media': { [tokens.mediaQuery.desktop]: { display: 'none' } },  // PC: Floating element entirely hidden
  },
  variants: { position: { bottom: { bottom: 32 }, stackOne: { bottom: 64 }, stackTwo: { bottom: 112 }, hidden: { opacity: 0 } } },
});
```

The visibility of the same share button is **dually controlled by two mechanisms: JS (`isMobile` → position calculation) and CSS (`@media display:none`).** Answering "Why isn't this button visible on PC?" requires navigating through multiple code sections, despite being a simple question.

### 3. Allowing Duplicate Code — Coupling

The [original text](https://frontend-fundamentals.com/code-quality/code/examples/use-bottom-sheet.html) shows a commonized hook that is repeated across multiple pages and issues a warning:

```typescript
// Toss Original — Commonized maintenance bottom sheet hook
export const useOpenMaintenanceBottomSheet = () => {
  const maintenanceBottomSheet = useMaintenanceBottomSheet();
  const logger = useLogger();
  return async (maintainingInfo: TelecomMaintenanceInfo) => {
    logger.log("Maintenance bottom sheet opened");
    const result = await maintenanceBottomSheet.open(maintainingInfo);
    if (result) {
      logger.log("Maintenance bottom sheet 'receive notifications' clicked");
    }
    closeView();
  };
};
```

> If there's a possibility for behavior to differ across pages, allowing duplicate code without commonization is a better choice.

We violated this principle in the opposite direction. We commonized two layouts into one file, reasoning that "PC and mobile are the same screen," but actual requests come in separately.

```typescript
// Our Code — Before: OrderSkeleton.tsx, 37 ternary operations for isMobile
export const OrderSkeleton = () => {
  const isMobile = useIsMobile();
  return (
    <>
      <Skeleton width="100%" height={isMobile ? 46 : 62} borderRadius={isMobile ? 0 : 4} />
      <Space size={isMobile ? 0 : 40} />
      <Skeleton width={isMobile ? 144 : 130} height={isMobile ? 32 : 24} />
      {!isMobile && <div className={styles.line} />}
      {isMobile ? <div className={styles.divider} /> : <Space size={48} />}
      <Skeleton width={160} height={isMobile ? 18 : 22} />
      <Space size={isMobile ? 2 : 4} />
      {/* …37 such ternary operations throughout the file */}
    </>
  );
};
```

This is the result of trying to put two completely different skeleton layouts into one function "without duplication." If duplication is allowed, each file becomes straight-line code without conditions:

```typescript
// Our Code — After: Allowing layout duplication and creating two versions
export const OrderSkeleton = () => (
  <>
    <MobileView><OrderSkeletonMobile /></MobileView>
    <DesktopView><OrderSkeletonDesktop /></DesktopView>
  </>
);
function OrderSkeletonMobile() {
  return (
    <>
      <Skeleton width="100%" height={46} borderRadius={0} />
      <Skeleton width={144} height={32} />
      <div className={styles.divider} />
      {/* 0 conditional branches — reads straight from top to bottom */}
    </>
  );
}
// OrderSkeletonDesktop is also the same — 37 ternary operations disappear, leaving two simple lists
```

The ~500 lines and 26 `@media` blocks in Chapter 2 tell the same story. It's a structure where modifying a mobile design can break the PC version, a state where, as the original text says, "every time common code is modified, dependent code must be individually tested."

### 4. Revealing Hidden Logic — Predictability

The [original text](https://frontend-fundamentals.com/code-quality/code/examples/hidden-logic.html) gives an example of logging secretly embedded within a balance inquiry function:

```typescript
// Toss Original — Before
async function fetchBalance(): Promise<number> {
  const balance = await http.get<number>("...");
  logging.log("balance_fetched");   // Hidden behavior not predictable by name or return type
  return balance;
}
```

> Only logic that can be predicted by the function's name, parameters, and return type should remain in the implementation.

In our code, this "smell" manifests as **hidden device logic within components.** It's not apparent from the name and signature alone, but it hides or disappears internally:

```typescript
// Our Code — Before ①: A section that appears as if it would always render based on its name
export const RecentOrdersSection = () => {
  const isMobile = useIsMobile();
  const { data, isLoading } = useQuery(ordersQuery);
  const orders = data?.orders ?? [];
  // Mobile + no orders → the entire section disappears. The caller has no way of knowing this
  if (isLoading || (isMobile && !orders.length)) return null;
  return <section>…</section>;
};
```

```typescript
// Our Code — Before ②: Always present in JSX, but CSS secretly hides it on mobile
// SectionTitle.css.ts
export const title = style({
  display: 'none', // Default (mobile): Hidden — someone reading only tsx cannot know
  '@media': { [tokens.mediaQuery.desktop]: { display: 'block' } },
});
```

The `tsx` file cannot answer the question "Why isn't this title visible on mobile?" — the hidden logic is in the CSS. The improvement is the same as in the original text: **reveal the hiding mechanism in the name and call site**, rather than inside the implementation:

```typescript
// Our Code — After: Conditions moved to the call site, device-specific nature indicated by wrapper/name
{(!isMobile || orders.length > 0) && <RecentOrdersSection orders={orders} />}

<DesktopView>
  <SectionTitle>Order Details</SectionTitle>  {/* Instead of CSS's secret display:none */}
</DesktopView>
```

I believe clean code remains important because human review is still necessary for AI-generated code.
It will serve as a crucial benchmark for us to establish a unified direction.

| Readability    | Separate code that doesn't run together | `isMobile ? A : B` interleaved in ~370 places — code for two devices mixed in one function |

### Research Findings

To summarize the research findings in one sentence: **Everyone is doing it differently.** From pure media query responsive (Coupang, 29CM) to JS branching (Ohouse Store), user agent adaptive (Kurly, Musinsa), and domain separation (Olive Young Korea), all are actively in use.

The reason everyone has made different choices is likely due to the respective trade-offs, as shown below.

| Method                        | Advantages                                                                  | Disadvantages                                                                                             | Adoption Cases                                     |
| ----------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| **① CSS Media Queries** (Single DOM) | SSR-safe (server doesn't need to know device) · Zero-runtime · Immediate response to resize | Limited expression if DOM structure differs significantly · Complexity explosion with accumulated branches per selector | Coupang · 29CM · Ohouse Home · Our product list    |
| **② `display:none` Dual Render** | Branches even structurally different UIs with CSS only · Simple implementation | Dual DOM/bundle transmission · SEO duplicate content · Significant waste if more than one screen's worth (accessibility is safe with `display:none` — 5-4) | 29CM GNB · Ohouse local fragments · Our header/order list |
| **③ JS Branching** (`matchMedia` hook) | Renders only one DOM · Clearly expressed with logic                         | SSR initial value issue → hydration mismatch or 2-pass render (slow) · Flickering/CLS before determination | Ohouse Store · Our `useIsMobile` 374 times         |
| **④ Server User Agent Detection** | Accurate from first render · No opposite code transmitted (bundle -38.7% measured case) · Safe hydration | No response to viewport resize · Risk of tablet/new user agent detection                                  | Kurly · Musinsa                                    |
| **⑤ Component/Route Separation** | File = 1:1 mockup · Parallel work possible · Each file is a single layout without `@media` | Requires branching point design (needs to combine with ④ for full SSR) · Risk of duplicate common logic/copy modifications | Our `DesktopHeader`/`MobileHeader` · Velog route separation measurement |

## Essential Considerations for Responsive Implementation

To approach how to develop, I felt it was necessary to first understand the problems that inevitably arise regardless of the chosen method, to make an informed decision. So, I investigated at least these points first.

### 1. Bundle Size

Media query and dual-render methods mean mobile users download all PC code (and vice-versa).

Here's an important distinction: merely "detecting" the server user agent does not reduce the bundle size. Our app already uses user agents (for app webview detection, bot detection to select SSR streaming strategy), but none of this is linked to the bundle. Bundle composition is determined by the static import graph at build time, so even if the server knows the device, the bundle size remains the same unless "which JS to send" is differentiated. Detection combined with serving separation (route separation or dynamic import) is required to reduce it.

### 2. SEO

-   Google uses mobile-first indexing — the mobile DOM must be the complete version of the content.
-   `display:none` dual rendering creates duplicate content. While crawlers read hidden content, if the management of the two versions diverges, it becomes ambiguous which one is the canonical version.
-   User agent detection can serve different HTML to Googlebot user agents (mobile/desktop versions), requiring careful caching management to avoid being mistaken for cloaking.

### 3. Hydration Mismatch

This is an inevitable issue when using JS branching (③) in SSR. Since the server doesn't know the device, it fixes an initial value (we use `desktop`), and if this differs from the client's determination, React throws a mismatch. A safe workaround, 2-pass rendering (`isHydrated` gate), incurs the cost of **flickering and CLS** instead. Our footer is precisely paying this cost:

```typescript
// Footer app download section — appears only after hydration → late pop-in, CLS
{isHydrated && platform !== 'APP' && (
  <>
    <div className={styles.appBannerDesktop}>…QR code…</div>
    <div className={styles.appBannerMobile}>…store badge…</div>
  </>
)}
```
