오늘은 헛짓거리한 썰을 써 보려고 합니다.


TL분과 1 on 1 때 FE 쪽에서 개선할 과제들 같은 걸 찾아서 진행해 달라고 말씀해 주셨습니다. 


주변에서 우리 웹이 너무 느리다는 말이 있었고, LA 페스타에 직접 참여했을 때도 현장에서 웹 초기 로딩이 너무 느린걸 경험했습니다.


병렬로 잡고 있는 일이 너무 많아서 정신없었지만 저에게는 Claude라는 신뢰하는 친구가 있었고, dev 서버에서 FCP 지표 위주로 POC를 올리는 데 효과 있는 작업을 찾아내기 위해 노력했습니다(Claude가).


측정 방법은 현재 dev 서버를 직접 브라우저로 접속하여 타임라인별로 걸리는 현재 지표를 파악했고, 각 POC 브랜치들을 배포하며 브라우저로 직접 측정하여 비교하도록 했습니다.


그러다가 무려 FCP를 약 30% 개선한 POC를 발견하게 되었습니다.

> 진짜 헛짓거리한 거라 도움되는 얘기 하나도 없습니다.

## 어떤 작업이었나?


저희 회사는 vanilla-extract CSS 라이브러리를 사용하고 있습니다. 


해당 라이브러리는 여러 개의 CSS 파일을 생성하게 되고 메인 화면에 진입할 때 최대 48개의 CSS 파일을 요청하고 있었습니다. 


POC는 해당 CSS 파일들을 번들링할 때 디자인 시스템 패키지별로만 묶어 주는 작업이었습니다.


| 지표 (Fast 4G) | 기준선   | 묶은 뒤  | 변화   |
| ------------ | ----- | ----- | ---- |
| 첫 화면 CSS 파일  | 48개   | 26개   | −46% |
| FCP          | 1.90초 | 1.36초 | −28% |
| LCP          | 2.09초 | 1.55초 | −26% |
| 첫 로드 JS      | 변화 없음 | 변화 없음 | 0%   |


처음 POC의 결과를 봤을 때는 이해할 수 없었습니다. STG의 preview 환경에도 배포해 보고 브라우저에서 직접 측정해 봤지만, 압도적으로 FCP가 빨라졌습니다. 

> 혹시 몰라서 다시 얘기하지만, 이 글은 헛짓거리한 얘기입니다. 사실 안 빨라졌습니다.

이게 왜 이렇게까지 효과를 가져오지..? Claude를 때려가며 이유를 파악하려고 노력했습니다.


## 왜 개선이 있었나 


Claude를 때려가며 설명해 내라고 했습니다. 


### **응답 편차**


파일이 많으면 그중 하나가 CDN 캐시 미스 등으로 늦을 확률이 커집니다.


⇒ 그럴 수는 있지만 말이 안 됩니다. 30% 정도의 FCP 향상이 매번 나오는 게 이상했습니다.


### **요청마다 드는 CPU 비용**


저사양 Android에서는 파일마다 하는 요청 처리와 스타일시트 처리가 쌓일 수 있습니다.


⇒ 저는 M4 정도의 괜찮은 맥북으로 테스트했으니 이것도 말이 안 됐습니다.


모르겠습니다. 하지만 효과가 30% 있는 것을 직접 측정했으니 팀원들에게 공유하고, Jira 티켓도 만들고, 다음 주에 작업해서 배포하겠다고 했습니다.

### React Router v7(Vite) 번들러의 문제인가?


React Router v7 SSR이 너무 마이너해서 이슈가 안 나온 걸까? 싶어 Remix 블로그 등을 조사해 봤지만, 오히려 과거에 esbuild 시점에 CSS 파일을 하나로 묶어서 오는 이슈가 있었으며 Vite 번들러를 사용하면서 필요한 JS의 청크별로 가져올 수 있게 되며 효율적으로 바뀌었다고 적혀 있었습니다.


### vanilla-extract의 문제인가?


FE 개발하면서 이전에는 Tailwind(하나의 CSS 파일), Emotion(JS 런타임) 등의 라이브러리를 사용했 CSS 파일 자체가 여러 개가 된 경험이 없었습니다.


vanilla-extract 는 컴포넌트마다 import * as styles from './Button.css.ts' 처럼 스타일 파일을 import 합니다. 빌드할 때 이 파일이 CSS 로 바뀌는데, 그 CSS 는 해당 컴포넌트가 들어간 JS 청크를 따라갑니다(Vite cssCodeSplit). 그래서 CSS 파일 수는 컴포넌트 수가 아니라 스타일을 가진 JS 청크 수와 같아집니다.


이 동작 자체가 문제일까 싶어서 github issue들을 찾아보고 vanilla-extract를 활용한 디자인시스템 라이브러리 [https://github.com/seek-oss/braid-design-system](https://github.com/seek-oss/braid-design-system)들을 살펴봐도 관련 문제를 찾을 수 없었습니다.


점점 .. 더.. 미궁 속으로 빠져듭니다.

## 처음부터 다시 해보자..


애초에.. CSS를 묶는다는 거 자체가 너무 위험하다는 생각도 계속 들었습니다.


Tailwind는 원자 클래스를 모아 CSS 하나를 만들고, 안 쓰는 CSS도 있지만 재사용으로 최적화되며, 우선순위 충돌 날 일 자체가 없습니다.


그러나 vanilla-extract는 컴포넌트 단위로 CSS를 요청하고, 컴포넌트가 많을수록 요청이 N개로 늘어나며, Tailwind처럼 하나로 묶으면 원자 재사용이 아니라서 우선순위 문제도 발생하게 됩니다. 


그리고 이런 해결 방법이라면 실제로 이슈가 올라와 있거나 관련 블로그 글이 있을 테데, 하나도 찾지 못했습니다.


처음부터 다시 측정해 보자는 마음으로, 새로운 세션에서 처음부터 다시 분석해 보기로 했습니다.
